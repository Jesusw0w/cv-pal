# Security policy

## Reporting a vulnerability

Please report security issues **privately**, not as a public issue.

- Open a [private security advisory](https://docs.github.com/en/code-security/security-advisories/guidance-on-reporting-and-writing-information-about-vulnerabilities/privately-reporting-a-security-vulnerability)
  on the repository.

Please include what you did, what happened, and what you expected. A proof of concept
helps but is not required.

This is a personal project maintained in spare time. Expect an acknowledgement within a
week. There is no bug bounty.

## Scope

CV Pal is self-hosted software: **you run it, on your infrastructure**. There is no
hosted service holding anyone's data, so the interesting reports are ones affecting the
software itself — authentication bypass, injection, path traversal in uploads, cross-user
data access, or anything that would let one account reach another's CVs.

Out of scope: findings against the public demo (it is the mock build, stores nothing,
and has no backend), missing hardening headers on a deployment you control, and reports
generated by a scanner without a demonstrated impact.

## What the software does to protect data

Documented so you can verify the claims rather than take them on trust. Details and
reasoning are in [docs/PLANNING.md](docs/PLANNING.md).

- **Passwords** are hashed with **argon2id** (19 MiB, 2 iterations, 1 lane, per the
  OWASP Password Storage Cheat Sheet). Legacy bcrypt hashes are verified and
  transparently upgraded on the next successful login.
- **Password length and screening** follow NIST SP 800-63B: a 12-character minimum,
  screening against a common-password list, and rejection of passwords derived from the
  user's own email.
- **Sessions** use short-lived JWT access tokens plus opaque refresh tokens, of which
  only a SHA-256 hash is stored. Refresh tokens are single-use; presenting a spent token
  revokes every session for that user, on the assumption that the legitimate holder and
  a thief cannot both have spent it.
- **Password policy** imposes no composition rule, per SP 800-63B §3.1.1.2. Length,
  blocklist screening and context screening do the work.
- **Login is rate limited** per client, with exponential per-account backoff. Failures
  are counted for any submitted address, existing or not, so lockout cannot be used to
  discover which accounts exist. A failed lookup still performs a hash, so a missing
  account is not measurably faster than a wrong password. The per-client half depends on
  the bundled nginx overwriting `X-Forwarded-For` with the real peer address; put the
  backend behind a different proxy and it must do the same.
- **Validation errors do not echo the request.** A rejected registration returns what
  failed and why, never the value — which on that endpoint would be the password.
- **Registration can be closed.** Set `CV_PAL_ALLOW_REGISTRATION=false` once your own
  account exists; worth doing before exposing an instance beyond your own machine.
- **A content security policy** restricts the page to its own origin, with no inline
  script permitted. It does not prevent token theft via XSS, but it removes the usual
  ways such a flaw is exploited.
- **Uploads** are validated by magic bytes as well as extension, size-capped during the
  write rather than after, and stored under server-generated names, so a hostile
  filename cannot escape the upload directory.
- **Ownership is enforced inside the query**, so another user's record is
  indistinguishable from one that does not exist.
- **Containers run unprivileged**, with `no-new-privileges`, and the API is not published
  to the host by default — it is reachable only through the frontend's proxy.
- **The secret key has no default.** An instance that has not been configured refuses to
  start rather than signing tokens with a publicly known value.

## Known limitations

Stated plainly, because a security policy that only lists strengths is not useful:

- **Rate limiting is in-process.** With multiple workers the effective limit is
  multiplied by the worker count. Adequate for a personal instance; put a proxy in front
  for anything public.
- **Tokens are returned in the response body and the browser keeps them in
  `localStorage`**, not in `HttpOnly` cookies, so a cross-site scripting flaw in the
  frontend could read them. This follows from the bearer-token API design and is tracked
  for revisiting now that the container build serves the UI and API from one origin.
  What limits the damage rather than preventing it: access tokens expire in 30 minutes,
  refresh tokens are single-use, and presenting a stolen one after the legitimate holder
  has spent it revokes every session for that account.
- **No 2FA**, no account recovery, no email verification yet.
- **The upload directory is not virus-scanned.** You are uploading your own CV to your
  own machine, but this matters if you ever expose an instance to others.
